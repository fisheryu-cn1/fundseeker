# Fundseeker 持仓相似性量化评估 1.01 版设计方案

> 版本：1.01
> 基线版本：1.0（已归档于 `archive/v1.0/`）
> 最后更新：2026-07-16

---

## 1. 设计目标

在 1.0 版已实现的全量 K-Means 聚类基础上，引入**增量/全量双模式**聚类执行机制：

1. **日常默认使用增量计算**：在持仓结构未发生季度性大调整、产品池变化可控时，基于上一次全量计算的质心和 K 值，对当前产品集进行快速聚类更新。
2. **自动监控聚类有效性**：对比本次运行与上一次基线运行的 silhouette、inertia 等指标，判断增量结果是否出现显著劣化。
3. **劣化时提示或自动切换全量**：当指标劣化超过阈值时，CLI/service 提示建议全量重算；在 `auto` 模式下可直接降级为全量计算。
4. **全量计算负责确定 K 值**：全量模式下通过 silhouette + inertia 肘部法则为每个算法（`kmeans-asset`、`kmeans-industry` 等）确定合理的 K 值，并持久化为后续增量运行的基线 K 值。
5. **增量运行锁定 K 值**：增量模式不再重新搜索 K，而是沿用基线 K 值，以保证簇的可比性和稳定性。

---

## 2. 现状评估（1.0 版）

### 2.1 当前执行方式：全量计算

1.0 版的 `SimilarityService.cluster()` 每次执行时：

1. 从 `product_holding` 加载指定报告期的全部持仓数据；
2. 构建产品 × 特征（asset/industry）权重矩阵；
3. 执行 A/C 份额合并；
4. 使用 K-Means++ 随机初始化质心；
5. 运行完整 K-Means 迭代；
6. 将结果作为新的 `similarity_cluster_run` 记录写入数据库。

**特点**：
- 每次运行都是独立的，不读取上一次运行的质心或 K 值；
- `--k auto` 时基于 silhouette 在 `[k_min, k_max]` 范围内搜索；
- 历史运行全部保留，用于跨运行对比，但不存在「基线」概念。

### 2.2 全量计算的代价

- 时间复杂度：O(n×k×d×iter + n²)（silhouette 计算含 n² 距离矩阵）；
- 当产品数 `n` 较大或 K 搜索范围宽时，全量计算耗时明显；
- 每日/每周行情变化时，持仓特征并未改变，频繁全量重算性价比低。

### 2.3 为什么需要增量

- **数据更新节奏不同**：持仓季度披露，净值每日更新。聚类基于持仓，因此理想情况下只在持仓更新后重新聚类。
- **簇稳定性**：频繁全量随机初始化会导致同一产品在不同运行中被分到不同簇，影响可比性。
- **Agent 调度成本**：增量计算单次耗时更低，适合作为 agent 定时任务。

## 3. 核心概念

### 3.1 基线运行（Baseline Run）

每个 `(algorithm, report_date, product_type_filter)` 组合在**最近一次全量计算**后形成一条基线记录，包含：

| 字段 | 含义 |
|---|---|
| `cluster_run_id` | 基线运行 ID |
| `k` | 选定的聚类数 |
| `centroids` | 质心矩阵（JSON 序列化） |
| `feature_names` | 特征维度列表（asset codes / industry names） |
| `feature_type` | `asset` 或 `industry` |
| `silhouette` | 轮廓系数 |
| `inertia` | 簇内平方和 |
| `n_products` | 参与产品数 |
| `created_at` | 基线建立时间 |

基线信息持久化到 `similarity_cluster_baseline` 表。

### 3.2 增量运行（Incremental Run）

增量运行时：

1. 读取当前 `(algorithm, product_type_filter)` 的基线；
2. 将基线质心与当前特征空间对齐（新增特征补 0，缺失特征删除）；
3. 以对齐后的质心作为 K-Means 的**热启动初始化**（warm start）；
4. 在当前产品矩阵上执行有限次迭代（默认 `max_iter=30`，可通过配置调整）；
5. 输出新的 `similarity_cluster_run` 记录，但 K 值与基线一致。

### 3.3 有效性监控指标

增量运行完成后，与基线对比以下指标（任一指标触发阈值即视为劣化）：

| 指标 | 阈值字段 | 默认值 | 劣化判定 |
|---|---|---|---|
| `silhouette_min` | 本次 silhouette 绝对值 | `0.05` | `< 0.05` 视为簇结构不可接受 |
| `silhouette_drop_ratio` = (基线 silhouette − 本次 silhouette) / \|基线 silhouette\| | 相对下降比例 | `0.25` | `> 0.25` 视为相对劣化明显 |
| `inertia_change_ratio` = \|本次 inertia − 基线 inertia\| / 基线 inertia | 相对变化比例 | `0.50` | `> 0.50` 视为簇内离散度变化过大 |
| `n_products_change_ratio` = \|本次 n − 基线 n\| / 基线 n | 产品池变化比例 | `0.20` | `> 0.20` 视为产品池变化过大 |
| `feature_jaccard` = 当前特征 ∩ 基线特征 / 当前特征 ∪ 基线特征 | 特征空间重合度 | `0.80` | `< 0.80` 视为特征空间变化过大 |

在 `mode=auto` 下触发阈值时自动切换为全量计算；在 `mode=incremental` 下触发阈值时抛出异常，提示用户手动执行全量重算。

## 4. K 值自动选择（全量模式）

### 4.1 候选指标

全量模式下，在 `[k_min, k_max]` 范围内运行 K-Means，收集：

- `silhouette(k)`：轮廓系数，越大越好；
- `inertia(k)`：簇内平方和，单调递减。

### 4.2 肘部法则

为了自动选择合理的 K，采用**silhouette + log-inertia 曲率肘部综合评分**：

1. 对 silhouette 做 Min-Max 归一化到 `[0, 1]`，得到 `silhouette_norm(k)`；
2. 对 log(inertia) 曲线求二阶近似曲率，得到 `elbow_norm(k)`（曲率越大越接近肘部）；
3. 综合得分：`score(k) = silhouette_norm(k) + elbow_weight × elbow_norm(k)`；
4. 选择使 `score(k)` 最大的 `k` 作为最终 K 值。

`elbow_weight` 默认 `0.3`，可通过 `IncrementalConfig.elbow_weight` 调整。该公式在 silhouette（衡量簇内紧密度与簇间分离度）和 inertia 肘部（避免 K 过大带来的边际收益递减）之间取得平衡，比单纯使用 silhouette 更稳定。

### 4.3 边界约束

- `k` 必须在 `[k_min, k_max]` 范围内；
- 若 silhouette 全部为负或极不稳定，则回退到 `k_min`；
- 记录 K 搜索过程中的 `(k, silhouette, inertia)`，供前端「跨运行 Inertia 对比」图使用。

## 5. 数据模型变更

### 5.1 新增表 `similarity_cluster_baseline`

```sql
CREATE TABLE similarity_cluster_baseline (
    id BIGSERIAL PRIMARY KEY,
    cluster_run_id BIGINT NOT NULL REFERENCES similarity_cluster_run(id),
    report_date DATE NOT NULL,
    product_type_filter VARCHAR(100),
    algorithm VARCHAR(30) NOT NULL,
    k INT NOT NULL,
    feature_type VARCHAR(20) NOT NULL,
    feature_names JSONB NOT NULL,        -- 特征维度列表
    centroids JSONB NOT NULL,            -- k × n_features 质心矩阵
    silhouette NUMERIC(10,6),
    inertia NUMERIC(20,6),
    n_products INT NOT NULL,
    k_search_results JSONB,              -- [{k, silhouette, inertia}, ...]
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (report_date, product_type_filter, algorithm)
);

CREATE INDEX ix_similarity_cluster_baseline_run
    ON similarity_cluster_baseline(cluster_run_id);
CREATE INDEX ix_similarity_cluster_baseline_lookup
    ON similarity_cluster_baseline(report_date, product_type_filter, algorithm);
```

### 5.2 既有表扩展

`similarity_cluster_run` 增加字段：

```sql
ALTER TABLE similarity_cluster_run
    ADD COLUMN mode VARCHAR(20) NOT NULL DEFAULT 'full',   -- 'full' | 'incremental'
    ADD COLUMN baseline_run_id BIGINT REFERENCES similarity_cluster_run(id);
```

- `mode`：标识本次运行是全量还是增量；
- `baseline_run_id`：增量运行时指向其依赖的基线运行。

迁移脚本：`scripts/migrate_similarity_1.01.py`，用于在已有数据库上创建新表和字段。

## 6. 模块改动设计

### 6.1 `src/fundseeker/similarity/config.py`

新增增量相关配置：

```python
@dataclass
class IncrementalConfig:
    mode: str = "auto"                       # "auto" | "full" | "incremental"
    silhouette_min: float = 0.05
    silhouette_drop_ratio: float = 0.25
    inertia_change_ratio: float = 0.50
    n_products_change_ratio: float = 0.20
    feature_jaccard_min: float = 0.80
    elbow_weight: float = 0.3                # 肘部评分在 K 选择中的权重
```

说明：
- `mode` 作为默认值，可由 `SimilarityService.cluster(..., mode=...)` 和 CLI `--mode` 覆盖；
- 增量热启动复用 `ClusterConfig.max_iter`，无需单独配置 `warm_start_max_iter`；
- `auto` 模式下劣化时直接回退全量，`incremental` 模式下劣化时抛异常以强制人工确认。

### 6.2 `src/fundseeker/similarity/baseline.py`（新增）

- `kmeans_warm_start`：以已有质心初始化，执行 K-Means 迭代；

### 6.4 `src/fundseeker/similarity/service.py`

修改 `SimilarityService.cluster()` 签名：

```python
def cluster(
    self,
    report_date: date | str,
    product_types: tuple[str, ...] | list[str] | None = None,
    k: int | str | None = None,
    save: bool = True,
    feature_type: str = "asset",
    mode: str = "auto",   # "auto" | "full" | "incremental"
) -> dict[str, Any]
```

执行逻辑：

1. 若 `mode == "full"` 或不存在基线 → 全量计算；
2. 若 `mode == "incremental"` → 必须存在基线，否则报错；
3. 若 `mode == "auto"`：
   - 尝试读取基线；
   - 若不存在 → 全量；
   - 若存在 → 评估是否适合增量（feature_jaccard、n_products_delta）；
   - 执行增量 → 监控指标；
   - 若劣化超过阈值 → 自动回退为全量；
   - 若全量完成 → 更新基线。

### 6.5 `src/fundseeker/similarity/persistence.py`

- 更新 `save_cluster_run(..., mode, baseline_run_id)` 以写入运行模式和基线依赖；
- 删除旧运行时，保留被其他运行作为 `baseline_run_id` 引用的基线运行，避免外键冲突；
- 基线读写由独立的 `src/fundseeker/similarity/baseline.py` 负责，`persistence.py` 不再重复封装。

## 7. 增量执行流程

```
cluster(report_date, feature_type, mode='auto')
  │
  ├─ 构建当前 FeatureMatrix fm
  │
  ├─ 若 mode='full' → run_mode='full'
  │
  ├─ 若 mode='incremental' 或 'auto':
  │     ├─ baseline = load_baseline(algorithm, product_type_filter, feature_type)
  │     ├─ 若 mode='incremental' 且 baseline 不存在 → 报错
  │     └─ 若 baseline 存在 → run_mode='incremental', 否则 run_mode='full'
  │
  ├─ 若 run_mode='full':
  │     ├─ select_k_elbow(...) 选择 K
  │     ├─ kmeans(...) 全量计算
  │     ├─ save_cluster_run(..., mode='full')
  │     └─ save_baseline(...) 覆盖旧基线
  │
  └─ 若 run_mode='incremental':
        ├─ aligned_centroids = align_centroids(baseline, fm)
        ├─ result = kmeans_warm_start(fm.X, aligned_centroids)
        ├─ fallback_needed, diagnostics = should_fall_back_to_full(baseline, fm, result, cfg)
        │
        ├─ 若 fallback_needed:
        │     ├─ mode='incremental' → 抛出异常，提示执行全量
        │     └─ mode='auto' → run_mode='full'，重新执行全量流程
        │
        └─ 若未劣化:
              └─ save_cluster_run(..., mode='incremental', baseline_run_id=baseline.run_id)

返回包含 mode、baseline_run_id、incremental_diagnostics 的运行结果
```

## 8. 监控与告警

### 8.1 CLI 输出提示

增量运行完成后，CLI 输出 `incremental_diagnostics` 字段：

- `fallback_needed: false` + 所有 `checks[*].violated` 为 `false` → 正常运行提示；
- `fallback_needed: true` 且 `mode='auto'` → 已自动切换为全量计算并更新基线；
- `fallback_needed: true` 且 `mode='incremental'` → 抛出异常，提示用户执行 `--mode full` 重新计算。

### 8.2 Web 层展示

`similarity_index.html` 和 `similarity_run.html` 可显示：

- 本次运行是「全量」还是「增量」；
- 若增量，显示基线运行 ID 和指标变化；
- 若劣化，显示告警 badge。

本版本先完成 CLI/service 层实现，Web 展示作为后续可选增强。

## 9. 幂等与回滚

- 每次运行都生成新的 `similarity_cluster_run` 记录，不覆盖历史；
- 基线表通过 `(report_date, product_type_filter, algorithm)` 唯一约束，新全量计算会覆盖旧基线；
- 增量运行失败或劣化时，可以选择回退到全量，确保结果可用；
- 用户可通过 `--mode full` 强制全量重算并刷新基线。

## 10. 验证计划

1. **单元测试**
   - `align_centroids` 对特征增删的补齐/裁剪正确；
   - `kmeans_warm_start` 从已有质心出发收敛更快或结果稳定；
   - `select_k_elbow` 在模拟数据上选出预期 K；
   - `should_fall_back_to_full` 各阈值触发正确。

2. **集成测试**
   - 首次运行（无基线）自动走全量并建立基线；
   - 第二次运行（mode=auto）走增量，指标正常；
   - 修改产品池后运行，触发劣化并回退全量；
   - CLI `--mode full` 和 `--mode incremental` 行为正确。

3. **性能测试**
   - 对比全量与增量运行耗时；
   - 验证增量运行结果与全量运行结果在相同数据上的差异在可接受范围。

## 11. 风险与后续优化

| 风险 | 缓解措施 |
|---|---|
| 特征空间剧变导致增量质心不适用 | feature_jaccard 阈值 + 自动回退全量 |
| 大量新产品加入打乱原有簇结构 | n_products_change_ratio 阈值 + 自动回退 |
| 热启动陷入局部最优 | 保留 K-Means++ 全量作为基线，增量仅做轻更新 |
| 簇标签漂移 | 增量沿用基线 K，保持簇编号语义稳定 |
| 跨报告期特征差异大 | 每个 `(report_date, algorithm)` 组合独立基线 |

后续可考虑：
- Mini-batch K-Means 进一步降低大数据集增量成本；
- 基于产品变更比例的「部分增量」：只重新分配变更/新增产品；
- Web 层增加「建议全量重算」告警。
