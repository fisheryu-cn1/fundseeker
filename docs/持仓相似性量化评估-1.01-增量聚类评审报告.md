## 1. 评审结论与优先级

### 1.1 总体结论

1.01 版「增量/全量双模式聚类 + 有效性监控 + K 值锁定 + 自动回退」的主线已经按设计文档落地，模块拆分合理、配置层 (`IncrementalConfig`) 与核心层 (`baseline.py`) 解耦清晰、迁移脚本的 `IF NOT EXISTS` 保护也到位。

但：

- **存在 1 个 P1 死代码**：`mark_run_mode` 在 `save_cluster_run` 已写入同字段后被重复调用，沦为 no-op。
- **存在 1 个 P1 设计偏离**：增量计算实际仍是"对全部产品重新跑 K-Means 热启动"，并未实现「只重新分配变更/新增产品」意义上的真正增量；这与设计文档 11 章「后续可考虑：基于产品变更比例的部分增量」一致，但函数命名 `kmeans_warm_start` 容易给后续维护者误导。
- **存在多个 P2 工程性问题**：`select_k_elbow` 多跑一次 K-Means、空簇处理在 `kmeans` 与 `kmeans_warm_start` 之间不一致、`save_cluster_run` 的 prior-deletion 逻辑与 `mark_run_mode` 的耦合令人困惑、监控指标在 silhouette=None 时静默跳过等。
- **cron 入口未对齐**：`scripts/fundseeker_similarity.py` 调度脚本的 `cluster` 子命令没有暴露 `--mode`，意味着实际 agent 调度仍然走全量。

### 1.2 优先级清单

| 优先级 | 编号 | 主题 | 影响 |
|---|---|---|---|
| **P1** | #1 | `mark_run_mode` 为死代码，应删除 | 易误导维护者 |

## 2. 关键 Bug / 设计偏离（必须修复）

### 🚨 Bug #1（死代码）：`mark_run_mode` 在 `save_cluster_run` 已写入后被重复调用

**位置**：
- 定义：[src/fundseeker/similarity/baseline.py:266-278](../src/fundseeker/similarity/baseline.py#L266-L278)
- 调用：[src/fundseeker/similarity/service.py:306](../src/fundseeker/similarity/service.py#L306)
- 已写入同字段：[src/fundseeker/similarity/persistence.py:79-91](../src/fundseeker/similarity/persistence.py#L79-L91)

**问题描述**

`save_cluster_run` 已经把 `mode` 和 `baseline_run_id` 写入 `SimilarityClusterRun`：

```python
# persistence.py
run = SimilarityClusterRun(
    report_date=report_date,
    product_type_filter=product_type_filter,
    algorithm=algorithm,
    k=k,
    params_json=params,
    silhouette=result.silhouette,
    inertia=result.inertia,
    n_products=fm.n_products,
    n_features=fm.n_features,
    mode=mode,                      # ← 已写入
    baseline_run_id=baseline_run_id, # ← 已写入
)
session.add(run)
session.flush()
```

随后 service.py 立刻又调用 `mark_run_mode(cluster_run_id, run_mode, baseline_run_id)`：

```python
# service.py
cluster_run_id = save_cluster_run(
    ...,
    mode=run_mode,
    baseline_run_id=baseline_run_id,
)
if run_mode == "full":
    save_baseline(...)
else:
    mark_run_mode(cluster_run_id, run_mode, baseline_run_id)  # ← 同一字段再写一次相同值
```

由于 `save_cluster_run` 已经接受 `mode` 和 `baseline_run_id` 并写入，`mark_run_mode` 的调用对数据库没有任何效果。其内部 `session.commit()` 还会触发一次额外事务提交。

**修复建议**

方案 A（推荐）：删除 `mark_run_mode` 调用与定义，更新调用方注释说明 `save_cluster_run` 已承担该职责。

方案 B：把 `save_cluster_run` 内部不再接受 `mode/baseline_run_id`，将其提取到 `mark_run_mode` 中，由调用方决定何时写入。

**采纳方案 A 更简单**，因为它符合当前 API 表面最小改动原则。

### 🚨 设计偏离 #2（语义）：`kmeans_warm_start` 并不是真正的"增量"

**位置**：[src/fundseeker/similarity/clustering.py:332-395](../src/fundseeker/similarity/clustering.py#L332-L395)

**问题描述**

函数命名为"warm_start"暗示了真正的"增量更新"语义（只对新增/变化样本重算）。但实际实现：

1. 接受完整数据矩阵 `X: (n_samples, n_features)`；
2. 在**全部样本**上反复执行 assign-then-update 循环；
3. 仅以历史质心作为 K-Means 初始质心（warm start）—— 这与 `kmeans` 函数接收 `init="k-means++"` 或 `init="random"` 时的差异只是初始化方式不同。

设计文档 §11「后续优化」中确实写明："基于产品变更比例的『部分增量』：只重新分配变更/新增产品"。所以现状与设计意图一致，但函数命名易使后续维护者误以为已经实现了部分增量。

**修复建议**

短期：保持函数实现不变，重命名为 `kmeans_from_centroids` 或在 docstring 顶部显式声明：

> **本函数仅是"以历史质心为初始化的标准 K-Means"，并非真正的部分增量。** 对所有样本重新执行 assign-then-update 循环，但起始点稳定 → 收敛更快、结果更可重复。

中期：在 §11 落地"部分增量"时引入新的 `kmeans_partial_update` 函数。

## 3. 正确性与性能（重要）

### ⚠️ #3（性能）：`select_k_elbow` 在选定 K 上多跑一次 K-Means

**位置**：[src/fundseeker/similarity/clustering.py:317-322](../src/fundseeker/similarity/clustering.py#L317-L322)

**问题描述**

```python
best_idx = int(np.argmax(composite_scores))
best_k = ks[best_idx]

# Re-run kmeans for the chosen k to obtain a deterministic result object.
best_result = kmeans(X, k=best_k, seed=seed, max_iter=max_iter, tol=tol)
best_result.silhouette = silhouettes[best_idx]
```

注释解释是 "to obtain a deterministic result object"，但循环内部 `best_result` 已经是确定性的（同一 `seed`），完全可以在循环里捕获。

后果：选定 K 上的 K-Means 实际跑了两遍，全量模式耗时多 1 / (k_max-k_min+1)。考虑到 v1.01 在每次回退路径上都会调用 `select_k_elbow`（[service.py:195, 244](../src/fundseeker/similarity/service.py#L195) 与 [service.py:244](../src/fundseeker/similarity/service.py#L244)），这一浪费会被放大。

**修复建议**

在 `select_k_silhouette` 中同步返回"最佳 K 的 KMeansResult 引用"：

```python
for k in range(k_min, k_max + 1):
    result = kmeans(X, k=k, seed=seed, max_iter=max_iter, tol=tol)
    result.silhouette = compute_silhouette(X, result.labels, distances=distances)
    ...
    if score > best_score:
        best_score = score
        best_k = k
        best_result = result  # ← 已经是 best_result
```

然后 `select_k_elbow` 直接返回 `raw["best_result"]`，不再重跑。

### ⚠️ #4（正确性）：空簇处理策略在 `kmeans` 与 `kmeans_warm_start` 间不一致

**位置**：
- `kmeans`：[src/fundseeker/similarity/clustering.py:111-116](../src/fundseeker/similarity/clustering.py#L111-L116) — 重初始化为距所有现有中心最远的点
- `kmeans_warm_start`：[src/fundseeker/similarity/clustering.py:377-379](../src/fundseeker/similarity/clustering.py#L377-L379) — 保留旧质心

**问题描述**

```python
# kmeans.py
if np.any(mask):
    new_centers[c] = X[mask].mean(axis=0)
else:
    # Empty cluster: re-initialize to the point farthest from all current centers.
    dist_sq = _squared_distances(X, centers)
    farthest_idx = int(np.argmax(dist_sq.min(axis=1)))
    new_centers[c] = X[farthest_idx]

# kmeans_warm_start.py
if np.any(mask):
    new_centers[c] = X[mask].mean(axis=0)
else:
    # Empty cluster: keep the old centroid to preserve semantics.
    new_centers[c] = centers[c]
```

两种策略各有一定道理（增量场景希望保留簇语义，全量场景希望重激活），但实现里没有文档化选择依据。如果增量运行中某些簇因为产品池收缩而变空：

- 全量策略会让该簇质心"迁移"到远离其它簇的样本 → 簇标签语义漂移；
- 热启动策略会让该簇质心一直停在历史位置 → 簇内不再有任何成员，但 cluster_run_id/cluster_id 仍然占用 K 个槽位。

设计文档 §11「簇标签漂移」风险点提到希望"增量沿用基线 K，保持簇编号语义稳定"，倾向于"保留旧质心"。但当前实现在重复调用时（如每季度都跑一次），空簇质心长期不更新，下次重新进入也会保持该位置，可能永远不会重新聚集样本。

**修复建议**

- 引入 `empty_cluster_strategy` 参数（默认两种场景不同）；
- 或在 `_warm_start` 中加一个 `max_empty_iter`：连续 N 次空簇后强制重新初始化，避免永久"卡死"；
- 在 `ClusterProfile` 输出中标注 `is_empty=True` 的簇，便于前端展示和监控。

### ⚠️ #5（正确性）：`silhouette=None` / `baseline.silhouette=None` 时监控项静默跳过

**位置**：
- 静默替换 -1.0：[src/fundseeker/similarity/baseline.py:221](../src/fundseeker/similarity/baseline.py#L221)
- baseline silhouette 为 None 时跳过：[src/fundseeker/similarity/baseline.py:230-243, 246-259](../src/fundseeker/similarity/baseline.py#L230-L259)

**问题描述**

```python
# 当前 silhouette=None 时
current_sil = result.silhouette if result.silhouette is not None else -1.0
checks["silhouette_min"] = {
    "value": current_sil,
    "threshold": cfg.silhouette_min,
    "violated": current_sil < cfg.silhouette_min,   # -1.0 < 0.05 → True → 触发回退
}

# baseline.silhouette=None 时
if base_sil is not None and base_sil != 0:
    silhouette_drop = (base_sil - current_sil) / abs(base_sil)
    checks["silhouette_drop_ratio"] = {..., "violated": ...}
else:
    checks["silhouette_drop_ratio"] = {..., "violated": False}  # ← 静默不触发
```

`silhouette_min` 这一项用 `-1.0` 替换 None，恰好会强制触发回退（设计意图），但 `silhouette_drop_ratio` 和 `inertia_change_ratio` 在 baseline 字段为 None 时直接不参与判定：

- 历史数据迁移时如果某些 baseline 行没有 silhouette（旧版缺字段），新一次增量运行的指标退化不会被监控到。
- 设计 §3.3 没有提到 baseline 字段可空，因此应该视为必填；若为 None，应视为"基线信息不完整，需要全量重算"。

**修复建议**

- baseline 字段为 None 时直接强制 fallback，而不是把 `violated=False` 静默掉；
- 在 `diagnostics` 中输出明确的 `baseline_complete: bool`，方便前端/调度器判断是否可信。

`fundseeker_similarity.py` 的 docstring 与设计 §6.6 都把"聚类"作为 agent 调度入口。但实际：

### ⚠️ #7（规模化）：`select_k_silhouette` 预计算完整 O(n²) 距离矩阵无保护

**位置**：[src/fundseeker/similarity/clustering.py:202-209](../src/fundseeker/similarity/clustering.py#L202-L209)

**问题描述**

```python
# Precompute the full distance matrix once.
dist_sq = (
    np.sum(X * X, axis=1).reshape(-1, 1)
    + np.sum(X * X, axis=1).reshape(1, -1)
    - 2.0 * (X @ X.T)
)
dist_sq = np.maximum(dist_sq, 0.0)
distances = np.sqrt(dist_sq)
```

对 N=5000 产品的资产维度（≈几百到几千列），距离矩阵规模为 5000×5000 = 25M float64 ≈ 200MB；若 N=20000 则 3.2GB，直接 OOM。

设计 §2.2 明确把"全量计算代价大、需增量"作为动机之一，但全量本身的 K 搜索路径仍未做规模保护。

**修复建议**

- 在 `select_k_silhouette` 入口加 N 阈值（如 N > 5000）改用分块距离 + 抽样 silhouette 估算，或切换到 GPU/外部库；
- 至少在 N 超过阈值时打印 warning 日志，并在 CLI 输出中暴露 `used_distance_cache: false`。

### ⚠️ #8（可维护性）：`service.cluster` 全量执行逻辑重复

**位置**：[src/fundseeker/similarity/service.py:193-216, 240-265](../src/fundseeker/similarity/service.py#L193-L265)

**问题描述**

```python
# 首次全量（run_mode='full'）
if run_mode == "full":
    if k == "auto":
        selection = select_k_elbow(...)
        result = selection["best_result"]
        k_value = selection["best_k"]
        k_search_results = selection["results"]
    else:
        k_value = int(k)
        result = kmeans(fm.X, k=k_value, ...)
        k_search_results = None

# 增量 fallback 后再全量（auto 模式）
if fallback_needed:
    ...
    if k == "auto":
        selection = select_k_elbow(...)
        result = selection["best_result"]
        ...
    else:
        k_value = int(k)
        result = kmeans(fm.X, k=k_value, ...)
        k_search_results = None
```

两段几乎一字不差。后续若修改 K 选择算法或 K-Means 参数，必须改两处。

**修复建议**

提取内部辅助方法：

```python
def _run_full(self, fm, k, cfg, inc_cfg) -> tuple[KMeansResult, int, list | None]:
    if k == "auto":
        selection = select_k_elbow(...)
        return selection["best_result"], selection["best_k"], selection["results"]
    k_value = int(k)
    result = kmeans(fm.X, k=k_value, seed=cfg.random_seed,
                    max_iter=cfg.max_iter, tol=cfg.tol)
    return result, k_value, None
```

`service.cluster` 中调用两次即可。

## 4. 设计与工程性（次要）

### 💡 #9：`save_cluster_run` 删除/引用逻辑过于隐式

**位置**：[src/fundseeker/similarity/persistence.py:46-77](../src/fundseeker/similarity/persistence.py#L46-L77)

```python
referenced_ids = {
    row[0]
    for row in session.execute(
        select(SimilarityClusterRun.baseline_run_id).where(
            SimilarityClusterRun.baseline_run_id.isnot(None)
        )
    ).all()
}

prior_filter = [
    SimilarityClusterRun.report_date == report_date,
    SimilarityClusterRun.algorithm == algorithm,
    SimilarityClusterRun.k == k,
    SimilarityClusterRun.product_type_filter == product_type_filter,
]
if mode == "incremental":
    prior_filter.append(SimilarityClusterRun.mode == "incremental")

prior_runs = session.scalars(
    select(SimilarityClusterRun).where(*prior_filter)
).all()
for run in prior_runs:
    if run.id in referenced_ids:
        continue
    session.delete(run)
```

潜在问题：
1. `referenced_ids` 是对全表的扫描，未限定 `report_date/algo/k/filter`。当 `similarity_cluster_run` 行数达到百万级时，每次 `save_cluster_run` 都要加载所有 baseline_run_id，效率低。
2. 当 `mode="full"` 时，`prior_filter` 不附加 mode 条件 → 既有全量又有增量行都会被删除候选。但 `referenced_ids` 仅保护基线（即被增量引用为 `baseline_run_id` 的行）—— 其他增量行（无引用者）会被删除，可能误删用户手工 K 的运行记录。
3. `mode="incremental"` 时，只删旧增量行不删全量行 → 历史全量运行被累积（增量回退时新全量会覆盖）。

**建议**

- `referenced_ids` 查询加 `(report_date, algorithm, product_type_filter)` 过滤，限定候选集；
- 全量保存时，按设计意图应"覆盖"既有运行：直接将 `referenced_ids` 内保护列出来即可，不必再分 mode；
- 在 docstring 中明示策略。

### 💡 #10：fallback 无日志

**位置**：[src/fundseeker/similarity/service.py:233-241](../src/fundseeker/similarity/service.py#L233-L241)

`service.cluster` 在 auto 模式 fallback 时只更新 `run_mode` 和 `baseline_run_id` 变量，没有 `logging.warning` 或 `print`。生产环境调度无人值守时无法看到这次降级。

**建议**

```python
if fallback_needed:
    if mode == "incremental":
        raise RuntimeError(...)
    logger.warning(
        "Incremental clustering degraded, falling back to full recompute. "
        "diagnostics=%s", diagnostics
    )
    run_mode = "full"
    ...
```

### 💡 #11：`algorithm` 字段拼接规则未文档化

**位置**：[src/fundseeker/similarity/service.py:169](../src/fundseeker/similarity/service.py#L169)

```python
algorithm = f"{cfg.algorithm}-{feature_type}"
```

`cfg.algorithm="kmeans"`，`feature_type="asset"|"industry"` → `"kmeans-asset"` / `"kmeans-industry"`。这是 schema 的隐含约定，但仅出现在 service.py 一行。如果后续要支持 `minibatch-kmeans` 或 `dbscan`，需要在文档中说明命名规则。

**建议**

- 在 `ClusterConfig` 注释中明示 "algorithm name is suffixed by feature_type"；
- 或在 `save_cluster_run` 入口对 `algorithm` 进行校验，禁止出现连字符之外的特殊字符。

### 💡 #12：`params_json` 未包含 `k_search_results`

**位置**：[src/fundseeker/similarity/service.py:270-275](../src/fundseeker/similarity/service.py#L270-L275)

```python
params = {
    **self.config.to_dict()["cluster"],
    "feature_type": feature_type,
    "report_date": str(fm.report_date),
    "mode": run_mode,
}
```

`k_search_results` 仅作为 API 返回值，未持久化进 `params_json`。设计 §10「验证计划」提到"对相同数据上全量与增量结果差异"，如果未来要做可复现性审计，需要 K 搜索历史。

**建议**

```python
if k_search_results is not None:
    params["k_search_results"] = k_search_results
```

### 💡 #13：`feature_jaccard` 监控粒度可更细

**位置**：[src/fundseeker/similarity/baseline.py:170-175, 202-210](../src/fundseeker/similarity/baseline.py#L170-L175)

当前仅给出"集合重合度"一个标量。增量场景下，"新增哪些特征"（基线无 → 当前有）和"消失哪些特征"（基线有 → 当前无）对后续 `align_centroids` 影响不同：

- 新增特征：质心新列补 0 → 不影响已有样本的分配结果（仅引入零维）。
- 消失特征：质心对应列被丢弃 → 历史样本的特征值被截断，距离度量变化大。

**建议**

- `diagnostics["checks"]` 增加 `n_features_added` 与 `n_features_removed`，分别触发不同阈值；
- 或者改用非对称指标：`recall = inter / old` 与 `precision = inter / new`，单独监控。

### 💡 #14：增量运行仍写入 `n_features`，导致下游误判特征维度变化

**位置**：[src/fundseeker/similarity/persistence.py:86-88](../src/fundseeker/similarity/persistence.py#L86-L88)

`save_cluster_run` 把 `n_features = fm.n_features` 写入。该值在增量运行中反映的是当前特征数（可能与基线不同）。`similarity_cluster_run` 已有 `mode` 和 `baseline_run_id`，下游查询（如 web 跨运行对比）可以直接读 `baseline_run_id` 指向的基线记录获取对齐后的真实维度。但目前 web 层（design §8.2 提到的）尚未实现这一点。

**建议**

- 在 `save_cluster_run` 增加 `feature_alignment_diff` JSON 字段，记录新增/删除的特征名称，便于 web 层显示"本运行相对基线新增 N 个特征、删除 M 个特征"。

### ⚠️ 缺失的覆盖

对照设计 §10 验证计划：

1. **`select_k_elbow` 评分正确性**：当前只检查 `best_k` 在范围内，未验证合成得分公式。#3 的修复（多跑一次 K-Means）一旦改动，缺少回归测试。
2. **`kmeans_warm_start` 收敛性**：现有测试断言 `n_iter <= 2`，但未覆盖「特征空间变化导致初始质心不再合理时，热启动仍能收敛」的场景。
3. **auto-fallback 完整路径**：`service.cluster` 的 auto 模式从增量 → 触发回退 → 全量重算 → 覆盖基线 → 写库 是核心链路，完全没有集成测试。
4. **`save_baseline` 与 `load_baseline` 一致性**：未测试 JSON 序列化反序列化后质心是否完全一致。
5. **CLI `--mode` 行为**：未测试 CLI 在 `incremental` 无基线时的错误信息、`auto` 模式下 fallback 的输出格式。
6. **`mark_run_mode` 死代码**：现有代码反而会被误以为"重要"，误导后续开发。
7. **`save_cluster_run` referenced_ids 保留**：未测试有增量运行被引用时，全量保存是否会误删基线。

**建议**

补充一个集成测试模块 `test_incremental_service.py`：

- 用内存 SQLite + 临时 schema 跑端到端；
- 第一次运行 `mode=auto` → 期望写 baseline；
- 第二次运行 `mode=incremental`（同一数据）→ 期望不写 baseline 且 diagnostics `fallback_needed=False`；
- 第三次运行（修改产品池）→ 期望 fallback 到 full 并更新 baseline。
